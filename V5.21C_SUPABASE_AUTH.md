## 1. Diagnostic avant implementation

### Point d'entree actuel

- `index.html` est le point d'entree unique de l'application statique.

  - Google Identity Services
  - `libs/jszip.js`
  - `libs/xlsx.full.min.js`
  - `app.js`

### Ordre d'initialisation actuel

`init()` dans `app.js` fait aujourd'hui:

1. chargement des valeurs identite ;
2. persistance identite ;
3. application du branding ;
4. chargement de chaque entite depuis `data/*.json`, surcharge locale, normalisation, puis `persist(name)` ;
5. chargement des `settings` ;
6. chargement des evenements Google locaux ;
7. restauration de la session Google depuis `sessionStorage` ;
8. affichage cockpit ou Parametres.

- GitHub Pages reste le mode de deploiement cible.

### Stockage actuel des sessions Google Calendar

- token Google: `sessionStorage` via `deosSessionService` ;
- email Google: `sessionStorage` ;
- aucun backend Google ajoute.

### Version et cache

- version app centrale: `DEOS_VERSION` ;
- version sauvegarde: `DEOS_BACKUP_VERSION` ;
- cache busting HTML par `?v=` sur les fichiers statiques.

## 3. Choix techniques

- Frontend statique conserve ;
- aucun framework ajoute ;
- configuration publique Supabase separee dans `config.example.js` ;
- `app.js` merge cette config publique avec `state.settings.remoteSync` ;
- aucune nouvelle cle locale metier DEOS creee ;
- chargement de `supabase-js` uniquement si le mode distant est active et seulement en version figee `2.56.0` ;
- `file://` reste local-only ;
- mode Production explicitement bloque dans V5.21C.

## 4. Schema de securite

### Frontend

- aucun secret stocke ;
- seules `SUPABASE_URL` et `SUPABASE_PUBLISHABLE_KEY` sont acceptees ;
- debug distant desactive par defaut ;
- aucun token ni mot de passe dans les logs DEOS ajoutes par cette version.

### Backend SQL

- RLS activee sur toutes les tables creees ;
- aucun acces `anon` accorde aux tables ;
- fonctions centrales RLS:
  - `deos_workspace_role(...)`
  - `deos_is_workspace_member(...)`
  - `deos_can_write_workspace(...)`
- creation initiale securisee via `deos_initialize_workspace(...)` ;
- `deos_test_records` impose:
  - workspace membre ;
  - `owner_id = auth.uid()` a la creation ;
  - label commencant par `Test` ;
  - payload JSON objet ;
  - role ecriture limite a `owner/admin/contributor`.

### Guard frontend test-only

- `SupabaseRemoteAdapter` refuse les payloads non test ;
- whitelist de cles de payload ;
- rejection explicite des cles metier DEOS ;
- refus d'un `workspaceId` different du workspace actif.

## 5. Risques principaux

- `file://` ne peut pas porter proprement les callbacks Auth distants ;
- dependance CDN externe pour `supabase-js`, mais version epinglee et chargee uniquement a la demande ;
- aucun test reel contre un projet Supabase n'a ete execute ici ;
- l'initialisation du premier workspace reste a executer cote backend de test ;
- la resolution de conflit est preparee pour `deos_test_records`, pas encore pour les entites metier.

## 7. Architecture Auth

`DeosAuthService` fournit:

- `initialize()`
- `getSession()`
- `getCurrentUser()`
- `signInWithPassword(email, password)`
- `signInWithMagicLink(email)`
- `signOut()`
- `resetPassword(email)`
- `onAuthStateChange(callback)`
- `isAuthenticated()`

Comportement:

- initialise le client Supabase uniquement en mode distant de test ;
- bloque le mode Production ;
- bloque `file://` pour l'auth distante ;
- recharge le contexte `workspace/site/role` apres auth ;
- n'expose pas les tokens dans les logs DEOS.

## 8. Architecture workspace

- seul son premier workspace de test peut etre cree par le flux prevu.

## 10. Adapter distant

`SupabaseRemoteAdapter` expose:

- `listTestRecords(workspaceId)`
- `getTestRecord(id)`
- `createTestRecord(data)`
- `updateTestRecord(id, patch, expectedVersion)`
- `softDeleteTestRecord(id, expectedVersion)`

Contraintes:

- toutes les methodes sont asynchrones ;
- uniquement `deos_test_records` ;
- guard anti-donnees metier ;
- erreurs structurees ;
- conflit detecte via `version`.

## 11. Gestion des conflits

- champ `version` sur `deos_test_records` ;
- update conditionnel sur `expectedVersion` ;
- echec => erreur `CONFLICT` ;
- aucune ecrasement silencieux.
