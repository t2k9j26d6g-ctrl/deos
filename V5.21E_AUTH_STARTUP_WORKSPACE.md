# DEOS V5.21E - Connexion générale en mode distant et chargement automatique du workspace

Date: 2026-08-05
Base: DEOS V5.20.5 + V5.21B + V5.21C + V5.21D

## 1. Diagnostic du démarrage actuel avant correctif

### Ordre réel de chargement des scripts

Dans `index.html`, l'ordre est:

1. Google Identity Services
2. `libs/jszip.js`
3. `libs/xlsx.full.min.js`
4. `config.local.js`
5. `config.example.js`
6. `supabase-client.js`
7. `remote-adapter.js`
8. `app.js`

### Bootstrap principal

Le bootstrap de DEOS se fait dans `init()`:

1. chargement identité
2. persistance identité
3. chargement + normalisation + persistance de chaque collection locale
4. chargement des paramètres
5. `initializeRemoteServices({ silent: true })`
6. chargement Google local
7. wiring UI
8. `setView("cockpit")` ou `setView("settings")`

### Initialisation distante réelle

`initializeRemoteServices()`:

- détruit l'ancien service si nécessaire
- lit `resolvedRemoteConfig()`
- construit `deosRemoteRuntime`
- si la configuration n'est pas prête, reste en local ou non configuré
- sinon instancie `DeosAuthService`
- restaure la session via `DeosAuthService.initialize()`
- crée `SupabaseRemoteAdapter`
- s'abonne à `onAuthStateChange`
- recharge les `testRecords` si session restaurée
- réinitialise ensuite le runtime Liens

### Récupération de session actuelle

Dans `DeosAuthService.initialize()`:

- charge `supabase-js` depuis CDN si nécessaire
- crée le client avec `storageKey = sb-deos-test-auth`
- appelle `auth.getSession()`
- applique `INITIAL_SESSION`
- installe `client.auth.onAuthStateChange(...)`

### Chargement workspace / site / rôle actuel

Dans `DeosAuthService.refreshContext()`:

- lit `profiles`
- lit `workspace_members`
- lit `workspaces`
- lit `sites`
- jusqu'ici, le frontend prenait arbitrairement la première appartenance si plusieurs workspaces existaient

### Cause exacte du parcours incomplet

Le backend Auth et la restauration de session existaient déjà, mais le démarrage restait incomplet pour trois raisons:

1. aucun écran général de connexion n'orchestrait les états `mode local`, `test non connecté`, `test connecté`, `local temporaire` et `hors ligne`
2. le contexte distant chargé au démarrage n'était visible pratiquement que dans Paramètres
3. le frontend ne représentait pas explicitement le cas `authentifié mais workspace à choisir`, ni la récupération sélective des Liens distants sur navigateur neuf

Conséquence:

- un nouveau navigateur ouvrait DEOS sans signal de compte clair
- la session Supabase était techniquement restaurée mais peu visible
- la récupération du workspace et des Liens distants n'était pas guidée au démarrage

## 2. Architecture Auth retenue

### Service conservé

Le service existant `DeosAuthService` reste le point unique pour:

- initialisation du client Supabase
- restauration de session
- validation utilisateur
- chargement profil / workspace / site / rôle
- événements Auth
- déconnexion

### Extensions V5.21E

Ajouts côté service:

- `profile` exposé dans le snapshot
- `availableWorkspaces` exposés dans le snapshot
- `requiresWorkspaceSelection()`
- préférence technique de workspace via une clé locale hors données métier:
  - `deos_remote_workspace_preference`
- `selectWorkspace(workspaceId)`

### Événements gérés

Le flux reste compatible avec:

- `INITIAL_SESSION`
- `SIGNED_IN`
- `SIGNED_OUT`
- `TOKEN_REFRESHED`
- `PASSWORD_RECOVERY`
- `USER_UPDATED`

Le listener principal ne se duplique pas:

- `initializeRemoteServices()` commence par `disposeRemoteServices()`
- une seule souscription Auth active à la fois

## 3. États de démarrage

### A. Mode local

Conditions:

- `DEOS_REMOTE_CONFIG.enabled = false`
- ou mode distant désactivé dans les paramètres

Comportement:

- aucun écran de connexion général
- aucun appel réseau Supabase
- chargement local immédiat
- badge `MODE LOCAL`

### B. Mode test - non connecté

Conditions:

- mode distant activé
- configuration prête
- aucune session valide

Comportement:

- overlay général `Connexion à DEOS`
- aucune donnée distante affichée comme active
- possibilité `Continuer temporairement en mode local` en Test uniquement
- message clair sur la disponibilité des données locales

### C. Mode test - connecté

Conditions:

- session valide
- utilisateur confirmé
- workspace chargé ou sélectionné

Comportement:

- profil / workspace / site / rôle chargés automatiquement
- overlay fermé automatiquement
- contexte distant visible dans la barre latérale
- proposition de récupération des Liens distants si navigateur vide

## 4. Règles du mode local temporaire

Le mode local temporaire:

- est autorisé uniquement en environnement Test
- ne désactive pas définitivement le mode distant
- ne supprime pas la configuration
- ne supprime pas la session
- charge le local
- affiche `TEST — LOCAL TEMPORAIRE`
- bloque les opérations distantes
- garde un bouton visible `Se connecter à l’espace DEOS`
- n'est pas persisté entre rechargements

Au prochain rechargement sans session valide:

- l'overlay général de connexion est reproposé

## 5. Chargement automatique workspace / site / rôle

### Cas simple

S'il n'existe qu'un workspace:

- il est chargé automatiquement
- le site associé est chargé
- le rôle est chargé
- la préférence technique est mise à jour

### Cas plusieurs workspaces

Si plusieurs workspaces existent:

- le frontend n'en choisit plus arbitrairement un sans information
- s'il existe une préférence technique valide, elle est reprise
- sinon l'overlay général demande explicitement la sélection du workspace

### Cas aucun workspace

Si aucun workspace n'existe:

- le frontend n'en crée aucun silencieusement
- il réutilise le parcours existant `Créer mon espace de test`

## 6. Navigation privée et nouvel appareil

Règle retenue:

- si le navigateur est vide localement mais que des Liens distants existent
- et que l'utilisateur est authentifié avec un workspace chargé
- une analyse distante des Liens est lancée automatiquement en lecture seule
- si aucun Lien local n'existe et qu'au moins un Lien distant existe, une proposition de récupération s'ouvre sans import automatique

Cette proposition:

- ne coche aucun Lien par défaut
- permet la récupération sélective
- ne lance aucune synchronisation continue automatiquement

## 7. Comportement hors ligne

Si le réseau est absent:

- l'accès local reste possible
- le message `Hors ligne — dernière session connue` est affiché dans l'overlay si nécessaire
- les opérations distantes restent bloquées
- la file Liens locale est conservée
- aucun échec réseau n'est transformé en `mauvais mot de passe`

Limite:

- le comportement exact dépend encore des scénarios réels de session restaurée hors ligne côté Supabase browser client

## 8. Comportement déconnexion

La déconnexion:

- appelle `signOut()` du service Auth existant
- réinitialise ensuite le service distant sans session
- vide le contexte distant en mémoire
- ne supprime pas les données métier locales
- ne vide pas tout `localStorage`
- conserve la file Liens locale
- repropose l'overlay général si le mode distant reste activé

## 9. Détection des Liens distants

V5.21E conserve la limitation aux Liens.

Après connexion:

- analyse locale/distante automatique autorisée en lecture seule
- aucune fusion automatique
- aucun envoi automatique des Liens locaux
- aucune activation automatique de synchronisation continue

Si le navigateur est vide localement et qu'un Lien distant existe:

- la proposition de récupération s'affiche
- la sélection reste explicite
- rien n'est récupéré sans confirmation utilisateur

## 10. Sécurité

Confirmations:

- aucune secret key ajoutée
- aucune `service_role`
- aucun mot de passe stocké par DEOS
- aucun access token journalisé
- aucune session complète journalisée
- la protection réelle reste côté backend / RLS
- aucun nouvel objet métier distant hors Liens

Mesures UI complémentaires:

- le champ `SUPABASE_PUBLISHABLE_KEY` est masqué visuellement en Paramètres
- `persistSettings()` ne réécrit plus `supabaseUrl` ni `supabasePublishableKey` dans la persistance métier exportable
- `config.local.js` reste la source publique locale de configuration test
